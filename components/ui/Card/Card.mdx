# Card

<ComponentLinks slug="card" />

Flexible content container. A default flexible content slot (no `layout`), plus five anatomy-driven arrangements via the `layout` prop: `stack` (vertical content card / `CardGrid` cell), `row` (horizontal content card), `metric` (compact stat), `control` (settings / integration row), and `pricing` (pricing tier). One flat slot set (`media` / `overline` / `title` / `children` / `action` / `badge`) serves all five, plus the per-layout extras each arrangement needs ([ADR-038](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-038-card-anatomy-over-preset-union.md)). The web-only `PricingCard` component is **deprecated as a standalone surface** — `layout="pricing"` below is its successor ([#2571](https://github.com/brikdesigns/brik-bds/issues/2571)).

> **Removed** — the `preset` discriminator (`control` / `summary` / `display` / `display-row`) has been replaced by `layout` (ADR-038 §5). Old→new mapping: `display`→`stack`, `display-row`→`row`, `summary`→`metric`, `control`→`control`.

> **Note** — Multi-card compositions (service grids, feature grids, blog rolls) live in the [`Card Grid`](?path=/docs/theming-blueprints-card-grid--docs) blueprint, not on this page. This page documents the Card primitive itself.

## Variants

The `layout` prop selects the arrangement. Default (no `layout`) gives a flexible `children` slot composable with `CardTitle`, `CardDescription`, and `CardFooter`. Each `layout` arranges the same optional slot set into a distinct shape.

The default shape also takes a `variant`: `outlined` (default, secondary border), `brand` (primary-color border), `elevated` (surface fill, no border, no shadow), `raised` (surface fill, no border, `--bds-shadow-raised` drop shadow), `borderless`, and `filled` (neutral recessed panel).

Cycle `variant` in the Controls panel on the story above — it is a fill/border treatment, not a distinct semantic variant, so it is a control rather than a story per [ADR-010](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-010-storybook-axes-of-information.md).

- `raised` — surface-primary fill, no border, with a cast `--bds-shadow-raised` drop shadow. The shadow-casting counterpart to the now-flat `elevated` (brik-bds#1146 / BACKLOG-493 removed `elevated`'s shadow so portal cards read flat). Use for a focal/lone card or a grid cell that needs a lifted, contained read.
- `filled` (class `bds-card--variant-filled`) — neutral recessed panel: `--bds-surface-secondary` fill with a `--bds-border-muted` border. Use for a grouping container that should read as part of the page rather than a raised object. Not a service-line wash — for that use `serviceLine`.
- `borderless` — transparent fill, no border, no shadow. Use for cards placed on a colored surface (service-tier or brand-image background) where the `outlined` border ring reads as visual noise. The card inherits the parent surface rather than forcing its own.

The default shape takes `serviceLine` / `serviceLineInverse` too, exactly as the `stack`, `row`, and `pricing` layouts do: `serviceLine` sets the pale `--bds-surface-service-{line}-light` wash, and `serviceLineInverse` swaps it for the theme-flipping `-inverse` surface. Both set only the fill, so the `variant` border stays — never hand-set `backgroundColor` for either.

### Leading media (avatar / image / logo)

The default shape takes an optional `media` prop that turns the card into a horizontal "media object" — an `Avatar`, a square 1:1 `Image`, or a bundled `Logo` on the left, with `children` stacked to the right. Pass exactly one of `media={{ avatar: {…} }}`, `media={{ image: {…} }}`, or `media={{ logo: { set, name } }}`. All size to the shared Avatar scale (`sm` 32px, `md` 40px, `lg` 48px, `xl` 64px) so they read at the same footprint. The avatar falls back to initials from `name` and can carry a presence `status`; the image takes `fit` (`contain` for artwork, `cover` for photos); the logo renders a full-color third-party / client brand mark. Mirrors the `TableAvatarCell` / `TableImageCell` / `TableLogoCell` media cells.

Which of the three renders is content, not a semantic axis — set `media` in the Controls panel on the story above rather than reaching for a per-media story.

### Stack layout

`layout="stack"` — vertical content card and the malleable `CardGrid` cell. Optional top `media`, an `overline` eyebrow, `title`, a `children` body, and a bottom-anchored `action`. All slots are optional so one arrangement serves any content type — service, blog post, customer story, property listing, team bio. `variant` / `serviceLine` set the surface for a cell on a colored grid; `serviceLineInverse` swaps the pale `-light` wash for the theme-flipping `--bds-surface-service-{line}-inverse` surface (white in light, deep hue in dark) — never hand-set `backgroundColor` for it.

<Canvas of={Stories.Stack} />

The `mediaTreatment` prop controls how the `media` slot relates to the card edge. `flush` (default) bleeds the media to the edge and pads only the body (`--bds-padding-lg`) — the blog/story/product-grid look. `inset` frames the media and body together in a single `--bds-padding-huge` inset — the service-card "card-vertical" look. Cycle it in the Controls panel on the story above.

### Pricing layout

`layout="pricing"` — a vertical pricing tier: optional top `media`, a `badge` + `title` header, the `price` / `period` block, a `children` body, a divider, the `features` checklist, and a bottom-anchored `action`. Supersedes the standalone [`PricingCard`](?path=/docs/deprecated-pricing-card--docs); see [ADR-038 § Amendment 2026-09-18](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-038-card-anatomy-over-preset-union.md) for why the pricing anatomy earns a layout rather than a `stack` recipe.

`price`, `period` and `features` are this layout's own slots — the same shape as `control`'s `connectionStatus` / `stamp` / `actionAlign`. The recommended tier is **not** a `highlighted` prop: set `variant="raised"` (or a `serviceLine`) so it composes from the one shared surface set like every other layout.

### Row layout

`layout="row"` — horizontal content card: `media` on the left, the text column (`overline`, `title`, `children` body, `action`) on the right. Use for single-row sections where a vertical layout wastes horizontal space: Related Customer Story, Recommended Add-On, featured plan. Toggle `imageWidth` between `narrow` (25%), `standard` (35%, default), and `wide` (50%) — or pass a CSS length / percentage. Collapses to a vertical stack at ≤ 640px.

#### Status and meta (`stack` and `row`)

`status` is a trailing indicator (a `Badge`, `Tag`, or `Dot`) and `meta` is a short fact line under the body (a `DateTime` or one fact). Neither renders an element when omitted. On `row`, `status` takes a trailing column (`bds-card__row-status`) and `meta` sits under the body (`bds-card__row-meta`); on `stack` they render as `bds-card__stack-status` / `bds-card__stack-meta`. `badge` stays the media-corner overlay on `stack`.

**Indicators vs actions** — an indicator goes in `status`, never in `action`. `action` is for a button or link the user can press; a Badge there reads as a control.

### Button emphasis on a card

A card holds at most one `primary`, and only when the card is the surface's call to action (an onboarding step, an empty-state CTA). A record card's own action is `secondary`. `ghost` is reserved for in-row and toolbar actions inside the card body.

### The standard, in one table

The classification the portal applies before any card is written. It composes display-choice (which display) with Card anatomy (which layout) and indicators (which pill).

| You have… | Render | Never |
| --- | --- | --- |
| Peer entities, each with its own link or button | `Card layout="row"` (list) or `"stack"` (grid): overline Tag · title · body · meta DateTime · status Badge · one action | an inline `<h2 style={heading.card}>`; a Badge in `action` |
| One record's own attributes | DataSection → FieldGrid → Field | a Card of label/value rows |
| Rows you compare down a column | Table in TableView | a Card around a table |
| One big number | `Card layout="metric"` (surfaced) / Stat (in a band) | a Field with a huge value |
| A number against a range or a fraction done | Meter (fraction text) / ProgressBar | "3 of 8" prose |
| A source with connect/sync/configure | `Card layout="control"`: logo · title · description · status · stamp · status-driven actions | a hand-rolled status string, a free-form "Synced …" |
| A wizard position | ProgressStepper | "Step 1 of 4" prose |
| A date on a card | DateTime `mode="relative"` (meta) or `"date"` (fact) | `toLocaleDateString`, `formatDate` |
| A form section or editor | DataSection in edit mode | an elevated Card per step |
| A surface-level warning | Banner | a Card with a red heading |
| Nothing yet | EmptyState in the view shell | a Card with "No X yet" |


### Metric layout

`layout="metric"` — compact stat card: an `overline` label above a large `title` value, with an optional trailing `action`. Context-neutral — a revenue figure, an active-user count, a storage total. Pre-format the value; the card applies no numeric formatting.

<Canvas of={Stories.Metric} />

Two optional slots extend `metric` for a labelled selection (the shape the removed `ProductSummaryCard` component folded into, ADR-038 §4): `media` renders a leading glyph (e.g. a `<ServiceTag>`) beside the stat, and `detail` renders a secondary line below the value (e.g. `price • frequency`). Both are additive — a plain stat omits them.

Inside, `metric` renders a Stat (`order="label-first"`): `overline` is its label, `title` its value, `detail` its detail line. Stat owns that anatomy, so `trend`, `meta`, `supplementary` and `description` are Stat props — compose `<Card><Stat /></Card>` when you need them.

```tsx
<Card
  layout="metric"
  media={<ServiceTag category="brand" variant="icon" size="lg" serviceName="Logo Design" />}
  overline="Interested in"
  title="Standard Logo Design"
  detail="$650 • one time"
/>
```

### Control layout

`layout="control"` — settings / integration row. Leading `media` (logo) + `title` / `description` on the left, (`connectionStatus` indicator + `action`) on the right. Use `actionAlign="top"` for long descriptions where the action should anchor to the upper-right corner.

`connectionStatus` accepts exactly `not-configured | connected | synced | negative | disabled` (`disabled` = Brik switched the source off: the card mutes and shows one "Enable" action). Retired `linked` / `syncing` / `failed` still map onto `connected` / `connected` / `error` for one minor. `stamp` (`{ kind, at, actor? }`, `at` an ISO 8601 timestamp) replaces `lastSynced` and renders through `DateTime`. Actions render in a `ButtonGroup`, driven by status: `onSetup` → "Setup" (not-configured), `onRetry` → "Retry" before `action` (error), `onEnable` → "Enable" (disabled). `readOnly` + `manageHref` replace every action with one "Manage on profile" link.
