[Content Rhythm](/docs/build-standards/content-rhythm) governs the vertical axis; this page governs the horizontal one. Every content band on a Brik page — a marketing section's container, a header, a footer, a consumer site's nav — is framed the same way: a `--content-width-*` band, centred, inset from the viewport edge by the canonical page inset. One recipe, so BDS sections and consumer containers stay flush-aligned at every breakpoint ([ADR-025](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-025-page-grid-standard.md)).

## The width-container recipe

Three declarations, always together:

```css
.my-container {
  max-width: var(--content-width-xl);   /* the band */
  margin-inline: auto;                  /* centred */
  padding-inline: var(--page-inset);    /* the page-edge inset */
}
```

`--content-width-xl` (1280px) is the default band — the value the section shell, `SiteHeader`, `Footer`, and the brikdesigns nav all resolve to. Narrower bands are a per-role choice from the [width roles table](#content-width-roles), not a new number.

The `lint-page-grid` gate fails any container rule whose `padding-inline` bypasses `--page-inset` — a container on an ad-hoc inset drifts out of alignment with every other band on the page.

## Page inset vs column gutter

"Gutter" names two different relationships. Only the page edge gets a dedicated token; space between columns is already governed by the [component rhythm map](/docs/build-standards/content-rhythm#component-rhythm).

| Sense | Relationship | Mechanism |
|---|---|---|
| Page inset | Viewport edge ↔ content band | `padding-inline: var(--page-inset)` on the container |
| Column gutter | Sibling ↔ sibling in a `Grid` or `Cluster` | The primitive's `gap`, from the `--gap-*` scale |

This is the gap-vs-padding rule from [Content Rhythm](/docs/build-standards/content-rhythm#gap-padding-or-margin) applied horizontally: gap is between siblings, padding is the edge.

`--page-inset` (renamed from `--gutter-page`; the old name survives as a deprecated alias) carries its own `[data-mode-spacing]` ladder over Primitives — `--space-600` at default, `--space-400`/`--space-800`/`--space-1200` for compact/comfortable/spacious — so it re-modulates under [spacing modes](/docs/foundation/spacing#spacing-modes) but does not vary with viewport width. It references Primitives directly rather than aliasing the Semantic `--padding-lg` ([ADR-025](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-025-page-grid-standard.md) amendment; a Semantic→Semantic reference is off the tier model). The stepped-not-fluid choice is deliberate: a fluid `clamp()` inset misaligns consumer containers from BDS section content at intermediate widths — brikdesigns shipped one and had to walk it back. In TS, import `pageInset` from `@bds-tokens` rather than writing the `var()` string inline.

## Content width roles

**One ladder caps everything horizontal**, and each rung carries exactly one role — stated in its name. A `-text-` rung caps a **text column**; a bare rung sizes a **band** ([ADR-041](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-041-one-content-width-ladder.md)).

| Token | Width | Caps | Role |
|---|---|---|---|
| `--content-width-text-xs` | 448px | text | Short intro — a single-line eyebrow + title |
| `--content-width-text-sm` | 600px | text | Section intro — title + description (the default) |
| `--content-width-text-md` | 720px | text | Long-form prose, rich-text body |
| `--content-width-sm` | 640px | band | Narrow band, focused forms |
| `--content-width-md` | 800px | band | Standard text-led body sections |
| `--content-width-lg` | 1024px | band | Feature grids, CTA bands |
| `--content-width-xl` | 1280px | band | The page band — hero, header, footer, most sections |
| `--content-width-full` | 100% | band | Full-bleed; prefer an explicit width |

The text rungs interleave numerically with the band rungs (600 < 640 < 720 < 800). That is expected and harmless: **pick a rung by its role, which the name states — never by sorting the ladder.**

There was a second `--measure-*` family in `ch` for the text column; ADR-041 retired it into the `-text-` rungs above, at the px widths it already rendered (the old names ship one more minor as deprecated aliases, then drop). Nothing in BDS scales body type (`--body-md` is a fixed 16px, only `--display-fluid-*` clamps, and `[data-mode-spacing]` never touches `font-size`), so `ch` never tracked anything — while two siblings sharing one `ch` cap at different type sizes resolved to two different pixel widths. Widths are **static across [spacing modes](/docs/foundation/spacing#spacing-modes)** either way: a readable line length is a typographic constant, not a density knob.

These are content constraints, **not** breakpoints — even where the pixel values coincide. For media queries use the `mediaQueries` export from `@bds-tokens` (or `breakpoints` for a raw width); CSS custom properties cannot appear inside `@media` conditions, so the `--breakpoint-*` CSS variables are reference-only.

<Callout type="warn">
  There is no responsive-spacing axis: density modes are the only spacing modulation in BDS. Do not introduce breakpoint-varying gutters or gaps.
</Callout>

## The column rule

> **A column has one content width and one left edge.** The element that OWNS the column sets the width; blocks nested inside it never re-cap themselves. Two caps in one column is the defect, not the fix.

This is the rule most often missed. A section's content container picks one rung and every block inside it inherits that column — a nested prose block, a hero block, a media block do **not** each declare their own `max-width`. Two caps in one column give the eye two different left edges and read as broken alignment, whichever tokens they use.

```css
/* ✅ one owner, one cap */
.split__content { max-width: var(--content-width-text-sm); }
.split__content > .prose { /* no max-width — inherits the column */ }

/* ❌ two caps, two left edges */
.split__content { max-width: var(--content-width-text-sm); }
.split__content > .hero  { max-width: var(--content-width-sm); }
.split__content > .prose { max-width: var(--content-width-text-md); }
```

If a block genuinely needs a different width from its siblings, it is not in that column — give it its own column, or restructure. Don't re-cap inside one.

## Text column vs band

A band width is not a text width. `--content-width-xl` (1280px) sizes the *band*; a title or description spanning the full 1280px is unreadable. The **text column** is the readable column *inside* the band — a narrower cap applied to the text group, not to the container.

Same ladder, two jobs — keep the jobs separate:

| | Sizes | Rung | Mechanism |
|---|---|---|---|
| **Band** | The container / section width | `--content-width-sm…full` | `max-width` + `margin-inline: auto` on the container |
| **Text column** | The text column inside it | `--content-width-text-*` | `max-width` on the text group — usually via `SectionHeader` |

### SectionHeader

Don't hand-roll the cap. A centered section intro — eyebrow / title / description above a card grid, a CTA band, a hero — is a `SectionHeader`: it composes [`ContentBlock`](/docs/build-standards/content-rhythm#where-each-step-is-set) for the slot rhythm ([ADR-023](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-023-content-blocks-and-prose-rhythm.md)) and adds only the measure + centering — the concern ContentBlock deliberately does not own.

```tsx
<SectionHeader
  title="What we do"
  description="From branding to websites to behind-the-scenes systems…"
/>
// centered · measure-md (--content-width-text-sm, 600px) · <h2> title at heading-lg — nothing to override
```

`measure` (`sm` / `md` / `lg`, default `md`) picks the cap; `align` (`center` / `start`, default `center`) picks whether the column centers in the band or anchors to its start. `SectionHeader` never sets a band width — drop it inside the section's width-container and it caps the text within. This is the single replacement for the ad-hoc measures a section header used to be written with (`600px`, `700px`, `width: 70%`, `max-width: none`, a reused band rung).

<Callout type="warn">
  A text column is not a band. Never cap a section intro with a **band** rung (`--content-width-sm…full` — those size the container) or with a raw px / percentage. Reach for `SectionHeader` — or a `--content-width-text-*` rung directly only when hand-rolling a text group `SectionHeader` doesn't cover. Reading a band rung's role as "prose" is what shipped [brikdesigns#1827](https://github.com/brikdesigns/brikdesigns/issues/1827); ADR-041 put the role in the name so the table can only be read one way.
</Callout>

## Where the recipe is set

Like the rhythm scale, you rarely write the recipe by hand — it is baked into the layer that owns each surface.

- **Marketing sections** → `.bds-blueprint-section__container` ([ADR-021](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-021-blueprint-section-shell.md)). Override band or inset via the section's hooks, never by hand-rolling a sibling container:

```css
.bds-cta__container {
  --bds-blueprint-section-content-width: var(--content-width-lg);
  --bds-blueprint-section-padding-inline: var(--padding-xl);
}
```

- **Product apps** → the `Page` primitive; its `padding` prop sets the shell inset (`lg` is the page gutter).
- **Full-bleed backgrounds with constrained content** → `Footer`'s `containerMaxWidth` shape: the background spans the viewport while `padding-inline: max(var(--page-inset), calc((100% - var(--content-width-xl)) / 2))` centres the content band.
- **Section vertical band** → unchanged from ADR-021: `padding-block: clamp(var(--padding-xl), 7vw, var(--padding-huge))`. A page is a stack of full-bleed sections; the vertical band is the clamp, the horizontal band is this recipe.
