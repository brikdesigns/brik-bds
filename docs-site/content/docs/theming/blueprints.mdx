## Catalog

The full enumerated library — every blueprint with moods, industries, layout spec, CSS hints, version, last-reviewed dates — rendered live from `@brikdesigns/bds/blueprints/library.json`. Coverage matrix shows section type × mood density at a glance; cells with `·` are gaps to author.

Every entry below is **renderable**: `is_active: true` asserts the key dispatches on at least one rail, and `validate:blueprints` enforces it. Designed-but-unbuilt layouts are not here — they live in `blueprints/blueprint-roadmap.json`, which carries no `is_active` flag so nothing can read it as an available-key set. A `·` in the coverage matrix is therefore a shipped-coverage gap, which the roadmap may already have a spec for.

## Two rails, one canonical

Blueprints ship on **two** renderers, and they are not peers. [ADR-037](https://github.com/brikdesigns/brik-bds/blob/main/docs/adrs/ADR-037-astro-is-the-canonical-blueprint-rail.md) §1 makes **Astro canonical**: it carries every published client site, so where the rails disagree, Astro's implementation is the reference and React is brought to it.

| Site class | Rail | Content source | Entry point |
|---|---|---|---|
| Standard client site | **Astro** (canonical) | in-repo content | `@brikdesigns/bds/blueprints-astro` → `<BlueprintDispatcher>` |
| Client site with a CMS or database; `brikdesigns.com` | React / Next.js | portal Supabase | `@brikdesigns/bds/blueprints-react` → `<BlueprintDispatcher>` |

React is a **supported** rail, not a lesser one — and it is the source of the composition *API* both rails now share. React named files by block with the layout as a prop first; ADR-037's 2026-09-08 amendment brought Astro onto that shape, so today a component is a **block** on either rail and `layout` is a prop. The `HeroLayout` / `CtaLayout` / `CardGridLayout` unions live in one framework-agnostic module (`astro/types.ts`) that both rails read, so a layout cannot be added to one rail only.

<Callout type="info">
  **Names carry layout, never content domain.** ADR-037 §4: a blueprint key describes layout shape only. `card_grid` is a key; a domain prefix naming the content it happens to hold is not, because the same grid renders team, blog and product collections. Industry and mood are metadata on the library entry; brand and atmosphere are tokens. Column counts and ratios are props. `scripts/lint-blueprint-naming.mjs` enforces this as `blueprint-key-context-word`, with no allowlist.
</Callout>

## Implementation

The Astro render surface the Theming tenet has always pointed at. Each blueprint key with a shipped Astro component is exported from this package; consumer Astro sites import the components directly or dispatch by key via `<BlueprintDispatcher>`.

See [BLUEPRINTS-ASTRO-PACKAGE.md](https://github.com/brikdesigns/brik-bds/blob/main/docs/BLUEPRINTS-ASTRO-PACKAGE.md) for the architecture contract, versioning policy, and scale-at-100-clients deployment topology.

### Package exports

```astro
---
// Consumer Astro page — the intended import shape.
import {
  SiteHeader,
  BlueprintDispatcher,
  // Individual blocks if you want direct imports:
  Hero,
  // Types:
  type BlueprintProps,
  type ClientFacts,
  type ResolvedTheme,
  type HeroLayout,
} from '@brikdesigns/bds/blueprints-astro';
---
<SiteHeader archetype={...} brandName={...} navItems={[...]} />
<main>
  <BlueprintDispatcher sections={page.sections}
                       clientFacts={clientFacts}
                       theme={theme} />
</main>
```

Types-only entry for contexts without the Astro runtime (e.g. the portal's scaffold task that plans compositions):

```ts
import type { BlueprintSection, KnownBlueprintKey }
  from '@brikdesigns/bds/blueprints-astro/types';
```

### Dispatch surface

| Component | Purpose | Props shape |
|---|---|---|
| `<BlueprintDispatcher>` | Reads `visualNotes.blueprintKey` per section and renders the matching component. Unknown keys fall through to `<BlueprintFallback>`. | `{ sections, clientFacts, theme }` |
| `<BlueprintFallback>` | Loud visible stub for unknown blueprint keys. Emits `data-blueprint-unknown-key` — CI greps client-repo builds for this attribute. | `BlueprintProps` |
| `<SiteHeader>` | Site-shell nav. Dispatches on the navigation archetype prop. v0.1 fully implements `editorial-transparent`; other archetypes render with a `data-unimplemented-archetype` attribute. | `{ archetype, brandName, navItems, phone?, primaryCta?, currentPath? }` |

### Shipped blocks

Eight components. A component is a **block**; the layout it renders in is a **prop**, never a filename — so twelve blueprint keys resolve onto eight files. Each follows the same `BlueprintProps` contract (`section` + `clientFacts` + `theme`), plus `layout` where the block has more than one.

`<BlueprintDispatcher>` owns the key → (block, layout) mapping, so a consumer that dispatches never picks a layout by hand.

| Component | `layout` | Library key | Section type |
|---|---|---|---|
| `<Hero>` | `split` | `hero_split` | `hero` |
| `<Hero>` | `interior-minimal` | `hero_interior_minimal` | `hero` |
| `<Hero>` | `with-pricing-card` | `hero_split_image_card_overlay` | `hero` |
| `<CardGrid>` | `card-grid` | `card_grid` | `services` |
| `<CardGrid>` | `two-column-list` | `two_column_detail` | `services` |
| `<Cta>` | `split` | `cta_split_contact` | `cta` |
| `<Cta>` | `default` | `cta_centered` | `cta` |
| `<About>` | — | `story_split` | `about` |
| `<Features>` | — | `feature_grid` | `features` |
| `<CalloutPanel>` | — | `callout_split` | `support_plan` |
| `<StatsDarkBar>` | — | `stats_bar` | `stats` |
| `<TestimonialsFeaturedLarge>` | — | `testimonials_featured_large` | `testimonials` |

The `HeroLayout` / `CtaLayout` / `CardGridLayout` unions are exported from the package and shared with the React rail, so a layout cannot be added to one rail only.

Unshipped keys render `<BlueprintFallback>` when the dispatcher encounters them — expected during the v0.1 → v1.0 incremental ramp. Each follow-up PR adds one or more components and removes its key from the fallback case.

### Contract per blueprint

Every blueprint component accepts **the same props shape**:

```ts
interface BlueprintProps {
  section: BlueprintSection;      // content: heading, body, items, cta, visualNotes
  clientFacts: ClientFacts;       // per-client: brandName, phone, heroImageUrl, etc.
  theme: ResolvedTheme;           // archetypes + atmosphere + theme mode
}
```

This uniformity is deliberate — the dispatcher is trivial (one lookup, one pass-through), every blueprint's surface is identical for authoring / review, and per-client customization happens through `ClientFacts` + CSS custom properties (not per-component props).

### Per-client CSS overrides

Each blueprint exposes documented CSS custom properties for per-client tuning — for example:

```css
.bp-hero-split-60-40 {
  --bds-hero-split-eyebrow-color: ...;
  --bds-hero-split-accent-line: ...;
  --bds-hero-split-image-radius: ...;
  /* ... more, see each component's header comment */
}
```

Per-client overrides MUST live in the client repo's `src/styles/client-overrides.css` with a `/* BDS-ISSUE: <url> */` comment on the preceding line. CI in each client repo enforces the comment requirement. See [spec §6.3](https://github.com/brikdesigns/brik-bds/blob/main/docs/BLUEPRINTS-ASTRO-PACKAGE.md#63-client-overridescss-escape-hatch--ci-gated-not-review-gated) for rationale.

### Non-hallucinatable content

Blueprints with `required_facts` render a visible `data-content-needed="<field>"` stub when the fact is null at render time — CI grep blocks publish. This is defense-in-depth; the portal's `dev_scaffold_site` task preflights `required_facts` before generating the client repo, so a missing fact should never reach the build stage.

### Verification

The package has a dedicated verification script at [`scripts/verify-blueprints-astro-exports.mjs`](https://github.com/brikdesigns/brik-bds/blob/main/scripts/verify-blueprints-astro-exports.mjs) that runs on every BDS pre-push:

1. Packs a tarball matching a real publish.
2. Creates a scratch Astro 5 project, installs the tarball.
3. `astro check` — type + import resolver.
4. `astro build` — SSR render to static HTML.
5. Asserts rendered HTML markers per blueprint.
6. `@axe-core/playwright` scan against every built page (WCAG 2.1 AA).
7. Confirms all expected files shipped in the tarball.

Any failure blocks the PR.

## Authoring

Blueprint edits flow **through BDS**. Portal admin edits (if kept) are drafts — landed changes flow back through a BDS PR. Full rules in [Architecture](https://github.com/brikdesigns/brik-bds/blob/main/blueprints/ARCHITECTURE.md).

Pick the file first — a layout with no component belongs in the roadmap, never the library:

| You are adding | File |
|---|---|
| A blueprint you are shipping in this PR (component wired on a rail) | `blueprints/blueprint-library.json` |
| A layout spec with nothing built yet | `blueprints/blueprint-roadmap.json` |

1. Edit the file the table names, on a task branch. Graduating a roadmap candidate **moves** it into the library — the validator rejects a key present in both.
2. Run `npm run validate:blueprints` (also runs as part of `npm run validate`). A library entry must dispatch on a rail; a roadmap candidate must not, and must not carry `is_active`.
3. Bump `version` on the affected blueprint(s) and the library envelope if the set changes. Update `last_reviewed` on confirmed-accurate passes — `review_cadence` is enforced, so a lapsed window fails the build.
4. Open a PR. Bridge edits, schema changes, and data additions stay separate.
5. After merge: publish the new BDS version, then bring the portal's `design_blueprints` across in **a new numbered migration**. `npx tsx scripts/generate-blueprint-seed.mts` regenerates `00114` in place, and Supabase does not re-run an applied migration — so regenerating alone changes the repo and never the database. A rename or a removal needs its own migration (`brik-client-portal/supabase/migrations/00390_rename_blueprint_keys_context_free.sql` is the worked example, from #2303). Tracked at [brik-client-portal#3952](https://github.com/brikdesigns/brik-client-portal/issues/3952).
