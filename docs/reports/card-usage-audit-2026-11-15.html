Card Usage Audit — 2026-11-15

Portal evidence read on brikdesigns/brik-client-portal@d530117ef (origin/staging, pinned to @brikdesigns/bds@0.239.0). BDS evidence read on brikdesigns/brik-bds@b6eec610 (main, v0.239.0). Every count below is a git grep over src/**/*.tsx on that portal commit unless the row says otherwise.

Verdict (HIGH confidence): the portal does not have a card-standards gap, it has a card-adoption gap plus four real holes in BDS. The canon that answers "which display does this data get" already exists (display-choice, dates-and-times, indicators, the v0.239.0 control-card contract from brik-bds#3159). 55 of 228 <Card> sites bypass it by declaring no layout; 42 distinct sites were classified and 24 of them are either a collection crammed into a card or a card anatomy re-typed by hand.

The four BDS holes: (1) row/stack layouts have no indicator slot, so every hand-rolled card puts a Badge where only an action fits; (2) Card layout="metric" and Stat are two spellings of one concept; (3) there is no fraction/step summary primitive, so "N of M" is hand-formatted in 7 places; (4) there are no chart tokens or chart components, so every number that is a trend or a part-to-whole is forced into a big-number tile or a label/value list.

3. Card anatomy — what the canon says, and the four holes

Card is one component with a layout axis (ADR-038): stack · row · metric · control · pricing, sharing one slot set (media · overline · title · children · action · badge) and one surface set (variant · tint · padding · interactive · href) — Card.tsx:14-324. The control layout additionally owns logo, status (five values), a typed stamp and a status-driven ButtonGroup (Card.mdx § Control layout, shipped in #3159).

3.1 Hole: row and stack have no indicator slot

Card.tsx:735-740 renders __row-media, __row-overline, __row-title, body and __row-action; stack adds __stack-badge (a media-corner overlay, :780). Neither has a place for a trailing indicator (status Badge, price, "Included in Plan"). That is why all 14 class-B sites hand-roll: the data has a status and the layout has nowhere correct to put it. Putting a Badge in action is the same misuse #6449 removed from DataSection actions.

AGENT DECIDED (revisable): add status?: ReactNode (an indicator: Badge/Tag/Dot, trailing) and meta?: ReactNode (a DateTime or a short fact line under the body) to row and stack, mirroring __control-status / __control-trailing, documented with the indicators-vs-actions rule — evidence: 14 of 42 no-layout sites re-type exactly this anatomy; display-choice already names "a trailing status" as a list-row property — revert: migrate class B onto InteractiveListItem rows instead and keep Card status-less.

3.2 Hole: Card layout="metric" and Stat are two spellings of one concept

Stat (Stat.tsx:10-20: value · label · detail · order · size) is documented as "wrap one in Card when it needs a surface". Card layout="metric" (Card.tsx:661, __metric-label · __metric-value · __metric-detail · __metric-action) renders the same three slots with its own CSS. The portal uses metric 146 times and Stat 0 times. ADR-033 is "one name per concept".

AGENT DECIDED (revisable): Card layout="metric" stays the consumer-facing name and renders a Stat internally; Stat gains the single-stat anatomy GitLab specifies (title · value · meta badge/trend · supplementary slot · description, see § 6) so both surfaces share it — evidence: 146 vs 0 adoption, one CSS block per slot today — revert: deprecate metric in favour of <Card><Stat/></Card>.

3.3 Hole: no fraction / step summary primitive

Seven sites hand-format "N of M": service-status-rollup.tsx:48, company-service-detail/projects-tab.tsx:112, details-tab.tsx:159, company-profile/sources-tab.tsx:627, admin/projects/[slug]/page.tsx:856, reporting/[reportType]/page.tsx:83, listings/business-listings-record.tsx:318. BDS has Meter (value/max, label, showValue; aria "N of M", Meter.tsx:144) and ProgressStepper (aria "Step N of M", ProgressStepper.tsx:311) but no visible "N of M" text form, and the portal consumes Meter 0 times.

AGENT DECIDED (revisable): a completion fraction is a Meter with valueFormat="fraction" ("3 of 8 tasks done"); a wizard position is ProgressStepper, never prose; the sentence form survives only as a Stat detail — evidence: the 7 sites, both components' aria strings already spell it — revert: ship a formatFraction content-system helper and keep Meter visual-only.

3.4 Hole: no chart layer

dist/tokens.css has no --chart-* token (grep -c -- '--chart' returns 0 on v0.239.0; the first publish's "comment hit at :1478" was a grep for "categorical" and that line is about --background-info, not charts). components/ui/ has Meter, ProgressBar, ProgressCircle and Stat, and nothing that draws a series. § 6.

5. Dates, times and feedback stamps

The canon exists and is specific: three shapes (date · timestamp · relative), rendered by DateTime; a Field value is never relative, a card meta line is relative (dates-and-times). A "Synced 11/4/2026" feedback stamp on a source is the control card's typed stamp ({kind, at, actor}), which renders through DateTime. Adoption: 12 DateTime renders against 64 bare toLocaleDateString, 106 formatDate( and 38 "Synced " strings. The "Since 11/4/2026" line on the client services card (dashboard/services/page.tsx:204,265) is a card meta line and should read "Since Nov 4, 2026" via DateTime mode="date", or relative, never a bare locale string.

AGENT DECIDED (revisable): no new date standard; the work is a portal migration ticket that retires formatDate/formatRelativeTime in favour of DateTime and widens no-bare-locale-datetime to flag formatDate( as well — evidence: the counts above, #6450 already widened the lint once — revert: keep the helpers and lint only new sites. The 64 toLocaleDateString sites are unverified as date-only columns; the lint says they pass, the audit did not re-check each column type.

6. Widening BDS for data: single stat, meters, charts

Vendor rules fetched this session (2026-11-15):

  • GitLab single stat — anatomy top to bottom: title (+icon) · value · meta icon or badge (variant success/warning/danger/info/neutral) · supplementary slot (progress bar or trend) · description (max two lines, truncated with tooltip). Use for "an overview of how a metric is performing" and "multiple metrics around a similar topic side-by-side"; do not use "to display the same metric over a period of time (use a chart instead)".
  • GitLab charts — column is the default and "favored over pie"; line for continuous data; area only for cumulated totals; bar = horizontal column; gauge for a value within a range; sparkline for "quick indication of trend" in limited space; legend only with more than one series; one series can never be toggled off; zoom bar only when the chart overflows.
  • Atlassian data-viz color — roles: title/legend color.text, ticks color.text.subtle, gridlines color.border, reference line chart.neutral, single series chart.brand; categorical 1..8 used in numeric order, capped at "5-6 by grouping"; status set success/warning/danger/information/discovery/neutral with a bold rung; 3:1 against the surface, a border between adjacent fills, no text on chart colour, never colour alone, dark mode by token.
  • Carbon — families Simple / Flow / Spatial (catalog, not a decision guide); dashboards: "most important data should have the highest contrast and occupy the largest area", F-shaped order, "consistent colors for each data set within a dashboard", all charts share layout, spacing and legend position.
  • Material — page renders client-side; the fetch returned no content. Not used as evidence.
