Foundations Modes Audit: spacing by device, clamp vs mode

Date: 2026-09-30 · Repo: brik-bds @ 519ed053 (main) · Figma: ❖ Brik Foundations Rkdc3SIWJUdgoAkeadgZZe and brikdesigns.com yhLkzLUnG71UFTgURDvgnv, read-only headless use_figma + get_variable_defs · Issue: brik-bds#2641 · Umbrella: brik-bds#2595 · Extends: the 2026-09-26 assessment (PR #2596) · Blocks: brikdesigns#1890

Status: PROPOSED — needs operator ratification. Every recommendation below is a proposal. The decisions in §9 are the operator's.

Verdict. Two defects are mixed together. One is in the model, and the bigger one is in adoption.

  1. No token in BDS varies by device through a mode. Every mode axis is a brand or density choice. Spacing has compact · comfortable · spacious. Typography has the same names plus expressive, and changes headings only. Breakpoint has 3 modes that carry identical values. Only --display-fluid-* and the section-shell padding react to screen width, and both use hand-written vw clamps.
  2. The same three mode names mean three different things in three collections. The portal adds a fourth vocabulary (base, expansive). This is the confusion an agent trips on. brikdesigns#1890 read density modes as device modes.
  3. Adoption is near zero. Across brikdesigns, brik-client-portal and 9 web/* repos:
    • no code sets data-mode-spacing;
    • nothing imports breakpoints, mediaQueries or --breakpoint-*;
    • about 300 @media lines hard-code px values such as 767, 991, 860 and 901;
    • the portal keeps its own spacing and type tables, and their values differ from BDS.

Recommendation (confidence: medium-high).

  • Keep the component spacing scale (--gap-*, --padding-*) the same at every screen width. Its modes stay a brand density choice. Every mature system we fetched does this.
  • Add one small layout tier that varies by device: section padding, page margin and grid gutter. In Figma it holds device modes (mobile · tablet · desktop) as endpoint values. The build emits clamp() between them, so values scale smoothly.
  • Keep the breakpoint collection, but collapse its dead modes.

This gives you smooth device scaling without crossing every spacing mode with every breakpoint.

1. Operator direction this audit answers

OPERATOR SAID 2026-09-30 (Claude Code session): "Spacing would be its own token collection for controlling padding and gap spacing throughout a brand - this would leverage modes to control fluctuating padding and gaps by breakpoint similar to typography."
OPERATOR SAID 2026-09-30 (Claude Code session): "that spacing scales smoothly between breakpoints - we need to determine clamp vs mode. … it does concern us to see that typrography tokens aren't referencing modes. … The mode naming suggestion for spacing makes sense - by device - we still think there's value in a breakpoint collection as these tokens can be referenced in our code vs a hard-coded valuel. … For mobile and tablet values we should be referencing industry standards - that's been asked before."

One premise needs correcting. Typography does not vary by breakpoint today, so "similar to typography" has no device-mode precedent to copy (§3). It does reference modes, but for brand expression, not device.

  • Headings change by mode, as a brand choice.
  • Display, body and label stay flat across modes. Display is mode-invariant by the ADR-013 amendment (#928).
  • By screen width: only the hand-authored --display-fluid-* tier scales (PR #961). Headings do not.

So the concern is valid in one sense. Nothing in typography varies by device except display, and display does it outside the mode system.

Figma and modes-spacing.css match rung-for-rung. The 0px collapse the 09-26 audit found is fixed: #2588 is CLOSED, and live Figma has gap/xs at 2 / 4 / 4 / 8.

The steps between modes are uneven.

  • Going from default to comfortable, gap-md jumps 4× (8 → 32) while gap-sm moves by only 2px (6 → 8).
  • gap-xl jumps from 48 to 104 going to spacious.
  • A density axis should scale more or less evenly, and this one doesn't. Nothing consumes these modes today, so the values have never been tested in a real layout.

What the fetched sources agree on:

  • No fetched system scales its core spacing tokens by screen width. Carbon, Primer and USWDS all keep the scale fixed and change only margins, gutters and the grid at breakpoints.
  • Utopia is the fluid-clamp() reference, and it interpolates between two values set by the designer.
  • Figma can store those two values but can't do the interpolation.

7. Clamp vs mode

OptionSmooth?Figma can hold it?Axes an agent must reason aboutVerdict
(a) Discrete device modes, switched by @mediaNo: steps at each breakpointYesdensity × device (the cross-product #2595 forbids)Reject
(b) Hand-written clamp() in CSSYesNo: design and code drift (§5 hand-rolled clamps, ADR-021's five drifted N values)1Reject. This is today's failure mode.
(c) Figma device modes hold the endpoints; the build emits clamp()YesYes1 (device), and only on the layout tierRecommend

Option (c) generalises two existing precedents instead of inventing one:

  • fluid-type.css anchors a vw clamp to on-scale min and max tokens.
  • ADR-021:35 gives every blueprint section padding-block: clamp(var(--padding-xl), 7vw, var(--padding-huge)).

What's new is where the endpoints come from (Figma device modes) and that a build step writes the slope. Today both are hand-picked in CSS.

9. Operator decisions

  1. D1: Amend the #2595 constraint. Its body line 42 reads "Tokens stay viewport-invariant … no cross-product of spacing × breakpoint modes" and carries no operator quote. Its line 43 is quoted and allows a semantic alias to vary "per client and per breakpoint".
    Recommend: amend it to "component spacing stays viewport-invariant; a layout tier varies by device; no token takes both axes." Confidence: high.
  2. D2: Spacing modes stay density; device modes go on a new layout tier. Your direction was "spacing modes by device". The industry evidence (§6) says to change only margins, gutters and section padding by device.
    Recommend: the layout-tier split. Confidence: medium-high.
  3. D3: Clamp vs mode.
    Recommend: option (c). Figma device modes hold the endpoints, and a build step emits clamp(). Confidence: medium-high.
  4. D4: Mobile and tablet design values. Page margin has an industry anchor (16 / 24px). Section padding doesn't, so it needs mobile and tablet frames from design.
    Recommend: design adds mobile (375 or 390) and tablet (768) frames for one page before the build.
