Interactive State System — 2026-11-21

Tracking issue: brik-bds#3300. Defect found along the way: brik-bds#3299.

WCAG does not require a border for a selected state. The border was a valid fix, but it reused the focus colour. So BDS now draws "selected" and "focused" the same way, which is the conflation you spotted.

  1. WCAG 1.4.11 asks for 3:1 against adjacent colours, not a border. Any visual cue can carry the state, and flat designs are allowed (§1). A fill swap inside a component is out of 1.4.11's scope, but it must still pass 1.4.1 (not colour alone).
  2. Selected = focus, literally. The SegmentedControl's selected border is --bds-border-brand-primary (SegmentedControl.css:88). The focus token is --bds-border-focus: var(--bds-border-brand-primary) (tokens/theme-brand-brik.generated.css:204). Both render rgb(227,83,53) (§5).
  3. BDS has no state model. The canon covers hover, press, focus, disabled and "selectable" (interaction-states.mdx). It does not define current, highlighted, expanded, read-only, invalid or loading, and it never says that selection must not use the focus channel.
  4. "Active" means five things. The --active class names selected, current page, keyboard highlight, drag-over and filter-applied across 14 components. CSS :active means pressed (§4).
  5. The drift is measurable. There are 4 focus-ring colour sources against 1 canon recipe, and the docs prescribe 18 different "selected" looks.
  6. The DatePicker / TimePicker triggers show no focus at all (WCAG 2.4.7) → #3299.

1. What WCAG actually says

All quotes come from W3C pages fetched 2026-11-21.

QuestionAnswerSource quote
Does a selected state need 3:1?Yes, against adjacent colours"any visual information necessary to indicate state, such as whether a component is selected or focused must also ensure that the information used to identify the control in that state has a minimum 3:1 contrast ratio." (1.4.11)
Must it be a border?No"It is possible to use a flat design where the status indicator fills the component and does not contrast with the component, but does contrast with the colors adjacent to the component." (1.4.11)
Must the selected state contrast with the unselected state?Not under 1.4.11 when they are not adjacent"This success criterion does not require that changes in color that differentiate between states of an individual component meet the 3:1 contrast ratio when they do not appear next to each other." (1.4.11)
Fill swap inside the component?Out of 1.4.11's scope, but 1.4.1 applies"The change of background within the component is not in scope of non-text contrast. However, this would not pass Use of color." (1.4.11, Figure 15)
What passes 1.4.1?A lightness change of ≥3:1, or an inverted foreground and background"if content is distinguished by inverting an element's foreground and background colors, this would pass" (1.4.1)
Is focus the same criterion?No. Focus is 2.4.7 (plus 2.4.13 at AAA) and must contrast too"even when a control does not need to have a visual boundary indicating its hit area, it will still need to have a sufficiently contrasting focus indication." (1.4.11)

For the SegmentedControl: the selected segment and the unselected segments sit next to each other, so the selected indicator needs 3:1 against the track around it. The white pill on the #f2f2f2 track is 1.12:1. That is why brikdesigns#1427 (closed) added the border in df146a75 (#2936). The border is one valid fix. A fill that clears 3:1 against the track is another, with no border.

Peer systems. GitLab Pajamas documents the segmented control as "a button group of equal options where only one can be selected and active". It does not document the selected visual (its Structure section reads "TODO:"). Base Web (Uber), Material 3 and Apple HIG returned empty pages to the fetcher. Their treatments are unverified, so this report draws no conclusion from them.

2. Proposed state model

This is a proposal. Each state gets one meaning, one ARIA attribute, one class word and one visual channel. No two states share a channel, so selected can never look like focus.

Retire --active as a state word. In CSS, :active already means pressed, so a class with the same word will always be misread.

3. Three separate questions: family, semantics, state

An earlier draft of this section filed SegmentedControl under "selection input". That was wrong. The docs taxonomy puts it in Control, not Form / Inputs (docs-site/content/docs/components/meta.json, the ---Control--- group). Method and limits

  • Component matrix: a script read every components/ui/*/*.css and *.tsx for state selectors and ARIA. 60 components carry an interactive selector. 34 of the 60 have no focus rule in their own CSS. Each of those may draw the browser's default ring or a composed child's ring, and they were not checked one by one. Only outline: none with no replacement is called a defect, and only DatePicker / TimePicker fit that.
  • Renders: all renders are local Chromium runs of the repo CSS. The hosted Storybook returned HTTP 401.
  • Docs sweep: grep over docs-site/content/docs, components/ui/**/*.mdx, docs/adrs, .claude/standards, docs/*.md, tokens/CASCADE.md and content-system. Key citations were spot-checked against the files.
  • Vendor: W3C 1.4.11, W3C 1.4.1 and GitLab Pajamas were fetched. Base Web, Material 3 and Apple HIG returned empty bodies and are unverified.
