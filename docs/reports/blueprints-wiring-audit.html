PROPOSED — needs operator decision. The answer in §2 and the cut list in §5 are recommendations. Nothing is removed or rewired by this report.

Verdict: not bloat. Keep blueprints, and build new client sites from them. Confidence: medium-high (about 75%).

The 2026-09-30 premise that "almost nothing is built from blueprints" is out of date. Since then the portal has wired the BDS resolver into the design decision set and the mockup prompt, and the scaffold emits BlueprintDispatcher into new sites. What is true: 0 of 8 existing sites use the dispatcher, they were hand-written before the rail existed. The dead weight is small and specific: two unused snippet fields, one uncalled route, and three stale docs (§5).

The one real fork is whether to also drop the portal's design_blueprints table. It still has 4 live read sites, so dropping it is a rewire, not a delete (§4).

2. Should client sites be built from blueprints?

Recommendation: YES for new scaffolds, no retrofit of the 8 existing sites. Confidence about 75%.

  • The scaffold already builds from them (scaffold-templates.ts:1861), and the portal's design decisions already rank them (decision-set.ts:643). Cutting blueprints now would remove working code, not dead code.
  • The existing sites are hand-written; retrofitting them is a per-site migration with no demonstrated need. That is a separate call from keeping the rail.
  • What lowers confidence: the scaffold's keys come from static compositions, not from the content step's choice, and no scaffolded site has shipped through it in the repos I could see. The "YES" in #2639's wording (wire scaffold to the content step's blueprints) is therefore still unbuilt.
